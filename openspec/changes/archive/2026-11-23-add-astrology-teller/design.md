# Design

## Context

Readings today come from `ChatService.drawFor` (`backend/agent/src/chat/service.ts`). It returns a tarot spread or an I Ching casting, which is stored as `ChatMessage.reading` (`chat/types.ts`), turned into teller input by `readingContext`, and shared with other tellers by `referenceContext` as raw JSON. Conversations accept only `SUPPORTED_DISCIPLINES = {tarot, i-ching}` and one or two tellers. Interactive kinds (fan, coin toss) live in `chat/interaction.ts` and `ChatService.applyInteraction`, with a public view that strips hidden state. The frontend renders readings in `frontend/app/src/app/message-body.tsx` and kinds in `card-fan.tsx` and `coin-toss.tsx`, after parsing them in `frontend/app/src/lib/*`.

Astrology differs in two ways. It needs stored personal input, and its result is computed from that input rather than randomized. See proposal.md for motivation and ADR-0018 for the durable decisions.

## Goals / Non-Goals

**Goals:**
- Charts that are reproducible and testable against reference data, computed entirely in-process.
- One chokepoint that decides how much of a chart a teller sees, shared by the reading context and the reference context.
- Reuse of the existing interaction machinery (saved state, compare-and-set updates, set-aside sweep) for the form kind.

**Non-Goals:**
- A general settings or profile system. The birth profile sits next to memory in the existing panel.
- Chart art beyond an SVG wheel. Call-overlay rendering is left out.

## Decisions

### 1. `backend/agent/src/astrology/` module (new)
- `ephemeris.ts` is a thin wrapper over `astronomy-engine`. `eclipticLongitude(body, utc)` uses `GeoVector` → `Ecliptic` for planets and `EclipticGeoMoon` for the Moon. Retrograde is the sign of the longitude change over ±12 h. `ascendantAndMidheaven(utc, lat, lon)` uses `SiderealTime` plus the local longitude for RAMC and the true obliquity: MC = atan2(sin RAMC, cos RAMC·cos ε) and ASC = atan2(cos RAMC, −(sin RAMC·cos ε + tan φ·sin ε)). Only this file imports the library, so it could be swapped later.
- `time.ts` provides `localToUtc(date, time, timeZone)`, built on `Intl.DateTimeFormat` offsets. It finds candidate offsets either side of the guess and returns `{ utc, note?: "ambiguous" | "skipped" }`. No time zone dependency is needed, since Node 20 ships full ICU.
- `chart.ts` is pure: `computeChart(details, now)` → `AstrologyReading { method: "natal-transits", computedAt, natal: { planets[], ascendant, midheaven, aspects[] }, transits[], note? }`. Signs come from `floor(lon/30)`. Whole-sign houses are `(signIndex − ascSignIndex + 12) % 12 + 1`. The fixed orb tables are in the spec.
- `catalog.ts` holds the original meanings and an `astrologyContentProvenance` constant, following `iching/hexagrams.ts`.
- `teller-view.ts` holds `chartForTeller(reading, { precise })`, the only serializer that turns a chart into teller text. Both `readingContext` and `referenceContext` call it for astrology readings, so Mira or Sage reacting to Astra's chart also get the coarse view under hosted replies. Today `referenceContext` passes `JSON.stringify(reading)` straight through. Without this function, that path would leak degrees.

*Alternatives considered.* The Swiss Ephemeris (`swisseph`) is a native AGPL addon, rejected in ADR-0018. Hand-rolled VSOP87 tables would mean more code and more risk for no gain. Placidus houses are undefined at high latitudes and the owner didn't ask for them.

### 2. Birth profile store and places
- `backend/agent/src/astrology/profile-store.ts` creates a `birth_profile` table (`user_id` PK = `local-user`, `birth_date`, `birth_time`, `place_id`, `consented_at`, `updated_at`), following `memory/store.ts`. It is tested with `pg-mem`.
- `backend/agent/data/places.json` is generated by `scripts/build-places.mjs` from GeoNames `cities15000`, `admin1CodesASCII` and `countryInfo`. Each row holds `[id, name, asciiName, region, country, lat, lon, tz, population]`. The file is committed (about 3 MB, 34k cities) and read from `backend/agent/data/` by both `src` and `dist`, so the build copies nothing. `places.ts` loads it once and searches by normalized prefix, ranking matches by population, with a limit of 10.
- Routes in `server/app.ts`: `GET /api/places?q=`; `GET /api/birth-details`; `PUT /api/birth-details` with body `{ date, time, placeId, consent: true }`, which returns 400 without `consent === true`; `DELETE /api/birth-details`. Validation lives in `astrology/details.ts` (real calendar date, not in the future, from 1800 on, `HH:MM`, a known `placeId`).

*Alternative considered.* Storing the profile as a memory item was rejected: memory needs memory consent, is embedded and is recalled into prompts. Each of those contradicts the privacy requirement.

### 3. Chat integration
- `SUPPORTED_DISCIPLINES` gains `astrology`. `drawFor` becomes async for astrology. It loads the profile and, if one is saved, returns `{ reading: computeChart(profile, new Date()) }`. If not, it returns a `needsDetails` marker.
- `runTurn`: when an astrology teller's route reads and there is no profile, in chat it calls `layOutBirthForm`, modelled on `layOutToss`. That function sets aside open forms from the same teller and saves a teller message holding the definition's `birthDetails.invitation` and an interaction `{ kind: "birth-details", state: "open" }`. In a call, the teller replies with a fixed app note in its turn context saying details can be added in the chat, and no reading is made.
- `chat/interaction.ts`: `Interaction` gains `BirthFormInteraction` (no hidden fields, so its public view is itself). `InteractionRequest` gains `{ action: "submit"; details: { date; time; placeId; consent } }`. `applyInteraction` validates the request, saves the profile, compare-and-sets the state to `submitted`, saves the computed chart on the form message, and streams the interpretation (as `applyToss` does). A repeat submission returns 409. The details are not written into the interaction state; only the state changes.
- `chat/types.ts`: `reading` adds `AstrologyReading`. `readingContext` gains an astrology branch: `chartForTeller` + the catalog meanings + "about 120 words, lead with the one or two transits that matter most".
- `precise = !hostedReplies || await memory.hasHostedConsent()`, which reuses the existing hosted-sharing gate.
- `createConversation` keeps its 1–2 teller limit.

### 4. Teller definition
- `tellers/schema.ts` gains an optional `birthDetails: { invitation }`, required when `discipline === "astrology"` and rejected otherwise (in `superRefine`, like `toss`).
- `tellers/definitions/astra.yaml`: id `astra-the-astrologer`, female, `call.voice: astra`, an activation profile around timing, transitions, career seasons and big decisions, `relationships` to Mira and Sage, and a reading lens and system prompt mirroring Sage's "interpret only what the application supplies" rules.
- The existing `service.test.ts` case that uses `astra-the-astrologer` as the example of an unsupported teller needs a new placeholder discipline (for example `numerology`).

### 5. Frontend
- `lib/astrology.ts`: `parseAstrologyReading` (ranges per the spec), `placementLabel`, and wheel geometry helpers.
- `app/chart-wheel.tsx`: an SVG wheel of 12 sign segments rotated so the ascendant sits at 9 o'clock, house numbers, and planet glyphs with collision nudging. A `<dl>` lists placements, aspects and transits. `message-body.tsx` dispatches on `method === "natal-transits"`.
- `lib/birth-form.ts` + `app/birth-details-form.tsx`: date input, time input, a place combobox calling `/api/places` with ARIA combobox semantics, a consent checkbox and the GeoNames attribution. The component is reused inline (submitting through the `interact` action) and in the memory panel (submitting through `PUT /api/birth-details`, with delete).
- `lib/tellers.ts` gains Astra with `model: "/tellers/astra/astra.vrm"`.

### TDD order
Tests come first in each step: the pure chart maths against reference charts (`tests/astrology/chart.test.ts`, with fixtures for one well-documented public chart and hand-checked DST and high-latitude cases), then time conversion, catalog completeness, the teller view (no degrees when coarse, never the raw details), schema rules, the profile store and routes (consent, validation, delete), places (offline, ranking), then the chat turn and interaction tests (form layout, submit, 409, set-aside, call branch, memory extraction not called, spans without content), then the frontend parsers and render tests.

## Risks / Trade-offs

- [Reference-chart tolerance flakes from ΔT or obliquity differences] → Compare against several sources, use the tolerances in the spec, and keep the reference data in fixtures with their source recorded.
- [Pre-1970 time zone data in ICU is coarse; local mean time births before about 1900 are off by minutes] → Note it in the catalog provenance and the ADR. The 1800 floor bounds it.
- [Degrees leak to a hosted model through other tellers' reference context] → A single `chartForTeller` chokepoint, with a test for Sage's reference input under hosted replies without sharing.
- [The 3 MB places file slows the backend's cold start] → Load it lazily on first search or chart, and check the load time once during the live check.
- [The router misses astrology phrasings ("what's my chart doing")] → Add routing cases for Astra in `router.test.ts`.

## Migration Plan

The change only adds things. The `birth_profile` table is created with `CREATE TABLE IF NOT EXISTS` at startup, so existing conversations are untouched. To roll back, remove `astra.yaml` and the discipline from `SUPPORTED_DISCIPLINES`. The table can stay. Assets (`astra.vrm`, the `astra` voice clip) are placed by hand, as documented in `docs/operations.md`.

## ADR alignment

ADRs reviewed: ADR-0001, ADR-0002, ADR-0004, ADR-0007, ADR-0008, ADR-0009, ADR-0012, ADR-0013, ADR-0014, ADR-0015, ADR-0017, ADR-0018

- **ADR-0013:** meets every item for a new discipline: an app-owned computation, an original catalog with provenance, a validated renderer with prose fallback, a definition and routing cases, and the supported-discipline set. No model-chosen data.
- **ADR-0002 / ADR-0007:** the ephemeris, places and storage are all local and single-user.
- **ADR-0009:** birth details are kept out of memory and memory extraction. Memory behaviour is unchanged.
- **ADR-0014:** hosted replies get the coarse chart unless the existing hosted-sharing opt-in is on. No new hosted call is made.
- **ADR-0017:** `birth-details` joins the closed catalog: its kind comes from app code, the payload is validated, the interaction is typed and idempotent, it is not chat or memory input, and invalid input falls back. ADR-0018 records why stating one's own facts fits within "results stay app-owned".
- **ADR-0008 / ADR-0012:** groups stay at two tellers, both respond, and readings are asked for in words.
- **ADR-0015:** Astra's call uses the existing local TTS and VRM path. The overlay uses its existing "see chat" fallback.
- **ADR-0004:** spans record that a chart was computed or a profile saved, with no birth data.
- **ADR-0018 (added in this change, Accepted by the owner before implementation):** records the astrology decisions above.
